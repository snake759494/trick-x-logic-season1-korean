> 저장소 안으로 옮겼습니다. 그 폴더는 원본 게임 데이터(`.sir0`·`.dat`)와 미리보기
> 그림뿐이라 지웠습니다.
>
> - **3절 포맷 명세는 지금도 그대로 유효합니다.** `tools/fonts.py`·`build_font_kr.py`
>   가 이 명세대로 구현돼 있습니다.
> - 2절의 산출물은 빌드 폴더에서 `python ../tools/fonts.py` 를 돌리면 `font_out/` 에
>   다시 뽑힙니다(`bootstrap.py` 로 `out/` 을 먼저 만들어 둘 것).
> - 5절의 시험 빌드(0x889F 부터 연속 재할당)는 흰 박스 문제로 버렸습니다. 지금은
>   **원본 한자 코드는 그대로 두고 그 자리에 한글 글리프만 얹습니다.** 자세한 내용은
>   저장소 첫 화면의 README 에 있습니다.

`Trick x Logic Season 1.iso` 에서 게임 내장 폰트 3종을 찾아 PNG로 추출했습니다.

## 1. 폰트 위치

게임은 PSP 시스템 폰트(`flash0:/font/*.pgf`)를 쓰지 않고 **자체 비트맵 폰트**를 내장합니다.
ISO 전체를 스캔했을 때 `PGF0` / `BWFON` 시그니처는 하나도 없었습니다.

```
ISO
└ PSP_GAME/USRDIR/data/common.bin      (98,342,912 B, "SECTPACK" 아카이브 / 928개 파일)
   ├ ./script/Font/NovelFontList.dat       536,576 B  무압축 SIR0
   ├ ./script/Font/AdvFontList.dat         272,384 B  LZ77 → 390,720 B SIR0
   └ ./script/Font/NovelRubyFontList.dat    14,336 B  LZ77 →  22,400 B SIR0
```

참고: `PSP_GAME/SYSDIR/BOOT.BIN` 은 전체가 0으로 채워진 더미이고, 실제 실행 파일
`EBOOT.BIN` 은 암호화(`~PSP`)되어 있습니다.

## 3. 포맷 명세

### 3.1 common.bin — "SECTPACK"

섹터(2048B) 단위 아카이브. 앞 20섹터(`0x0000`–`0x9FFF`)가 TOC이고 데이터는 섹터 20부터.

TOC 레코드는 가변 길이로 연속 배치됩니다:

```
char   name[];   // '\0' 종료, "./script/Font/..." 형태
uint16 id;       // 하위 15비트 = 파일 인덱스, 최상위 비트 = 압축 플래그
uint16 sector;   // 데이터 시작 섹터 (섹터 20 기준 상대)
uint16 count;    // 섹터 개수
```

파일 오프셋 = `(20 + sector) * 2048`. 928개 항목이 겹침 없이 EOF에 정확히 맞습니다.

### 3.2 압축 (id의 최상위 비트가 1일 때)

```
uint32 decompressed_size;
uint32 compressed_size;
uint8  stream[];
```

LZ77. 제어 바이트 1개마다 8개 토큰, **MSB부터** 읽고 비트가 **1이면 리터럴** 1바이트,
0이면 2바이트 매치:

```
length   = (b0 & 0x0F) + 3          // 3..18
distance = ((b0 >> 4) << 8) | b1    // 12비트
```

복사원은 `현재_출력_위치 - distance`이며, **스트림 시작보다 앞은 0으로 읽습니다**
(초반의 0 채움 구간이 이 규칙에 의존합니다).

### 3.3 SIR0 컨테이너

```
0x00 char   magic[4];      // "SIR0"
0x04 uint32 subheader_off;
0x08 uint32 pointer_list_off;
0x0C uint32 zero;
0x10 ...                   // 글리프 레코드들 (0x20부터 시작)
```

`subheader_off` 위치:

```
uint32 glyph_count;
uint32 zero;
uint32 offset[glyph_count];   // 각 글리프 레코드의 파일 오프셋(오름차순)
```

### 3.4 글리프 레코드

```
0x00 uint16 code;      // Shift-JIS (0x0020 .. 0xEA74), 오름차순 정렬
0x02 uint8  flag;      // 0 = 세로쓰기용 별도 자형이 뒤에 붙음, 1 = 가로 자형만
0x03 uint8  _;
0x04 uint8  w, h;      // 가로쓰기 글리프 크기
0x06 uint8  x0, y0;
0x08 uint8  x1, y1;    // h == y1 - y0
0x0A uint8  vw, vh;    // 세로쓰기 글리프 크기
0x0C uint8  vx0, vy0, vx1, vy1;
0x10 uint8  bitmap[];  // 4bpp, 낮은 니블 먼저, stride = ceil(w/2), 값 0..15
     uint8  vbitmap[]; // flag == 0 일 때만, stride = ceil(vw/2)
```

레코드 전체 크기는 **4바이트 정렬**됩니다(각 비트맵을 개별 정렬하지 **않음** — 세로 비트맵은
가로 비트맵 바로 뒤에 붙습니다). 3개 폰트 2,526 + 2,311 + 266개 레코드 전부
이 계산과 바이트 단위로 일치하는 것을 확인했습니다.

## 4. 한글 패치 시 고려사항

- **폰트에 한글 글리프가 없습니다.** 수록 문자는 Shift-JIS(JIS X 0208) 범위뿐입니다.
  한글을 넣으려면 안 쓰는 한자 슬롯을 교체하거나 글리프 테이블을 확장해야 합니다.
  글리프는 4bpp 안티에일리어싱에 본문 최대 22px라, 이 크기의 한글은 충분히 표현 가능합니다.
- 레코드가 **Shift-JIS 코드 오름차순**이라, 게임이 이진 탐색으로 글리프를 찾을 가능성이
  높습니다. 코드를 새로 넣을 때 정렬을 깨뜨리지 않도록 주의해야 합니다.
- 글리프 오프셋 테이블이 절대 오프셋이므로, 레코드 크기가 바뀌면 테이블 전체를
  다시 계산해야 합니다.
- `PSP_GAME/USRDIR/module/` 의 `jis2ucs.bin` / `ucs2jis.bin` (각 65536×2B)이
  Shift-JIS ↔ 유니코드 변환 테이블이라, 텍스트 처리 경로에서 같이 봐야 합니다.
- 재삽입 시 `common.bin` 을 다시 쓰려면 SECTPACK TOC의 `sector`/`count` 를 갱신해야
  합니다. 압축은 무압축(플래그 0)으로 저장해도 되지만, 섹터 수가 늘면 뒤쪽 파일이
  전부 밀립니다.

## 5. 한글 폰트 적용 (테스트 빌드)

`SeoulHangangEB.ttf` 로 완성형 2350자를 렌더해 심은 시험 빌드를 만들어 실기에서
확인했습니다. 시험 ISO 는 목적을 다해 삭제했습니다.

> **결과: 부분 실패 — 코드 할당 방식을 바꿔야 합니다.** 아래 "실기 확인 결과" 참조.

빌드 자체는 원본과 크기가 완전히 동일(718,307,328 B)했고, `common.bin` 영역만
제자리에서 덮어써 ISO9660 디렉터리 구조는 건드리지 않았습니다.

### 매핑 규칙

게임 폰트에는 실제 사용되는 한자만 들어 있어 슬롯이 부족했습니다
(NovelFont 2,137 / AdvFont 1,914 < 2,350). 그래서 한자 영역을 통째로 버리고
**0x889F 부터 연속된 Shift-JIS 2바이트 코드 2,350개**를 완성형 순서대로 할당했습니다.

| 완성형 index | 한글 | EUC-KR | → Shift-JIS |
|---:|:--:|---|---|
| 0 | 가 | 0xB0A1 | **0x889F** |
| 1 | 각 | 0xB0A2 | 0x88A0 |
| … | … | … | … |
| 2349 | 힝 | 0xC8FE | **0x94FC** |

전체 대응표는 `hangul_map.csv` 에 있습니다. 텍스트 삽입기는
`한글 → EUC-KR 코드 → 완성형 index → 위 Shift-JIS 코드` 로 변환하면 됩니다.
연속 구간이라 계산으로도 구할 수 있습니다.

ASCII·기호·히라가나·가타카나 글리프는 **원본 그대로 유지**했으므로 그대로 쓸 수 있습니다.
루비 폰트는 한자가 없어 손대지 않았습니다.

### 적용 결과

| 폰트 | 글리프 | 한글 | 글자 크기 | 저장 크기 |
|---|---:|---:|---|---|
| NovelFont | 2,739 | 2,350 | 20×20 | 244,145 B (120 섹터) |
| AdvFont | 2,747 | 2,350 | 17×17 | 196,198 B (96 섹터) |
| NovelRubyFont | 266 | 0 | 변경 없음 | 14,336 B (7 섹터) |

원래 폰트 3개가 쓰던 402섹터 구간에 223섹터만 사용합니다(여유 179섹터).
`NovelFontList.dat` 는 원래 무압축이었으나 압축 플래그(`id |= 0x8000`)를 켜서
압축 저장했습니다 — 같은 아카이브 안에서 동일 확장자 파일들이 플래그를 혼용하고
있어 로더가 범용으로 처리한다고 판단했습니다.

### 실기 확인 결과 (PPSSPP)

**동작한 것 — 파이프라인은 완전히 검증됨:**

- 한글 글리프가 화면에 정상 렌더링됨. 0x889F~0x94FC 범위에 있던 한자
  (예: 界 = 0x8A45)가 한글로 제대로 표시되는 것을 확인
- `NovelFontList.dat` 의 **압축 플래그 전환(`id |= 0x8000`)이 정상 동작**.
  범용 로더라는 판단이 맞았음
- 히라가나·가타카나·영숫자는 원래대로 정상 표시
- SECTPACK 재배치, ISO 제자리 패치 모두 문제없음

**실패한 것 — 코드 재할당 방식:**

0x94FC 를 넘는 한자(예: 落 = 0x977D, 冥 = 0x96BB)를 전부 지워버려서
해당 글자가 **흰 박스**(글리프 없음)로 표시됐습니다. 상용 한자 대부분이
0x94FC 위쪽에 있어 화면 곳곳이 깨졌습니다.

### 다음에 할 방식

한자 영역을 재할당하지 말고 **원본 한자 코드를 그대로 유지**한 채,
그 자리에 한글 글리프만 얹습니다.

- 슬롯은 NovelFont 2,137 / AdvFont 1,914 개로 2,350 에 못 미치지만,
  **번역이 끝난 뒤 실제로 쓰인 한글만** 넣으면 충분합니다
  (한국어 텍스트에 2,350 자가 전부 등장하는 경우는 드묾)
- 이 방식이면 슬롯을 늘릴 필요가 없어 파일 크기도 원본 범위에 들어갑니다
- 번역 완료 후, 사용 글자 집합을 뽑아 빈도순으로 슬롯에 배정하면 됩니다

따라서 폰트 작업은 **번역 이후로 미룹니다.**
